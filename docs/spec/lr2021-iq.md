# LR2021 raw I/Q: the hardware interface

How a host gets raw complex baseband out of a Semtech LR2021 (receive), and sends samples into its modulator
(transmit), over SPI. Semtech's datasheet doesn't document either path. This file states the facts the firmware's
LR2021 front end (`components/lr2021`, `esp_idf/main/fe_lr2021.c`) is written from.

## 0. Where the facts come from

- Semtech, LR2021/LR2022/LR2012 datasheet, DS.LR20xx Rev. 2.2 (29 Jul 2026): every documented command, its
  opcode and argument layout, the status word, FIFO flags and the extended FIFO registers. Cited as "DS 5.3.3".
- SAMS0N1TE/lr2021-sdr (<https://github.com/SAMS0N1TE/lr2021-sdr>), commit
  `929d97a1b14b9563f418d6f4fd84a787a56e45aa` (2026-10-18), GPL-3.0: its documentation (`docs/protocol.md`,
  `docs/porting.md`, `docs/extended-fifo.md`, `docs/live-streaming.md`, `docs/technical-overview.md`,
  `docs/tx-discovery.md`, `docs/tx-playback.md`) and the command sequences in its sources. Cited as "SDR". Only
  facts about the chip were taken from it: opcodes, register addresses, argument values, the order the chip needs
  them in, the sample format, rates and measured limits. No code, comments or code structure were taken; the
  implementation here is written from this file.

Everything marked SDR is reverse engineered on one board (a LilyGO T-Display-P4, ROM 1.24) and isn't in the
datasheet. It may not hold for another ROM. Findings with a board and date (R2.17 on, R3.9 on) were measured on
our W12.

Values that are choices rather than requirements are marked **(choice)**: the chip needs some value there, and
the one given is what SDR used or what we picked.

## 1. Preconditions

- **R1.1** The chip is an LR2021 with ROM (firmware) 1.24: GetVersion (0x0101) answers 0x01, 0x18 (DS table
  6-40). The raw paths are refused on any other version (SDR).
- **R1.2** No Semtech patch is running: the 32-bit word at memory address 0x800FF8 (ReadRegMem32, 0x0106) must not
  be 0x600DB002, the marker of an active patch (SDR; the patch loader's load address 0x801000 and the marker are
  also in Semtech's public patch driver). With a patch active the raw paths are refused.
- **R1.3** The host owns the radio for the whole session: no other modem, scan or packet work in between.
- **R1.4** Semtech's patch (USP's `pram_lr2021`, 560 words, type 3 version 0x13) loads with WriteRegMem32 in
  32-word frames from 0x801000 and starts with EnablePram (0x012D 0x00); afterward 0x800FF8 / 0x800FFC read
  0x600DB002 / 0x00031304. A reset removes it. With it running, the route command 0x0290 still answers OK: R1.2's
  refusal is the host's rule, not the chip's (W12, 2026-10-24). The ROM-side analysis is in the git-ignored
  `lr2021-patch.local.md`.
- **R1.5** Data RAM is not cleared by NRESET or at boot: after a reset 0x800FF8 reads near-random words (0xEFDC5BC3
  one time, 0xEFDCDBC3 the next), not the patch marker and not zero. A marker check right after a reset is
  meaningful only for the marker value itself (W12, 2026-10-24).
- **R1.6** Patch code runs only from SRAM bank 1 (0x801000, executed at 0x101000, 4 KB; code at 0x101F00 runs).
  Bank 2 maps into the code window (aux 0x80000008 [8:6] = 1) and loads from 0x102000 then read it, but executing
  there hangs the chip until NRESET, even after an instruction cache invalidate; so does Semtech's entry 1, which
  jumps there (W12, 2026-10-24). A load from 0x102000 with bank 2 unmapped also hangs it.
- **R1.7** ReadRegMem32 refuses some register addresses with a command error (0xF30180–0xF301FF, parts of
  0xF30880 and above); the answer bytes are then stale, so check the status before using them.
- **R1.8** The chip's CPU (ARCv2 EM, patch code) has the reduced 16-entry register file (RF_BUILD, aux 0x6E =
  0x4B02): r0–r3, r10–r15 and r26–r31 only; an instruction that touches r4–r9 hangs the chip. It runs at about
  28–32 MHz with no caches (I/D cache build registers 0): an add takes 35–45 ns, a 32×32 `mpy` or 16×16 `mpyw`
  about 100 ns, in a zero-overhead loop (W12, 2026-10-24).
- **R1.9** SetSleep and a patch don't mix. NSS must stay low 100 µs to wake the chip (DS 4.4.1; a 1 µs frame woke
  it once in four tries); the driver's `lr2021_wake` holds it 120 µs. With no patch loaded the chip wakes at once
  from SetSleep 0x02 (retention), but it comes back as from a cold start: words written at 0x800FF8 and
  0x801000–0x805800 read back as power-up contents, only 0x800900 as before. With Semtech's patch or ours loaded it
  doesn't wake at all, with retention or without: BUSY stays high past 3 s and only NRESET brings it back. The
  datasheet says the PRAM survives a sleep with retention (22.3). Reload a patch after a reset instead of sleeping
  with it (W12, 2026-10-24).

## 2. Receive

### 2.1 Set up a LoRa receiver first

The raw source sits in the LoRa receive chain, so the chip is set up as a LoRa receiver (all documented, DS 8.1,
9.9) before the route command, in standby:

| Step | Command | Arguments |
| --- | --- | --- |
| standby | SetStandby 0x0128 | 0x00 (RC) |
| packet type | SetPacketType 0x0207 | 0x00 (LoRa) |
| image calibration at the frequency | CalibFE 0x0123 | the frequency's 4 MHz cell (DS 6.4.2) |
| frequency | SetRfFrequency 0x0200 | Hz, 32 bits |
| RX path | SetRxPath 0x0201 | LF path, boost 0 |
| modulation | SetLoraModulationParams 0x0220 | `sf << 4 \| bw`, `cr << 4 \| ldro` |
| packet | SetLoraPacketParams 0x0221 | 4 bytes |
| sync word | SetLoraSyncword 0x0223 | 1 byte |

- **R2.1** The LoRa bandwidth sets the sample rate (2.3). `bw` is DS table 9-3's code: 0x2 for 31.25 kHz, 0x3 for
  62.5 kHz.
- **R2.2** Spreading factor, coding rate, packet parameters and sync word don't matter to the raw samples as far as
  is known. SDR used SF7 (`sf` 7), CR 4/5 with LDRO off (`0x10`), packet parameters `00 08 FF 02`, sync word 0x12
  **(choice)**.
- **R2.3** Check GetErrors (0x0110) after the setup: any error bit means the setup failed.

### 2.2 Route the samples to the RX FIFO

| Step | What | Source |
| --- | --- | --- |
| 1 | SetStandby 0x0128, 0x00 | DS |
| 2 | **route: opcode 0x0290, 11 bytes `FF 00 00 00 00 0A 00 00 00 00 01`** | SDR |
| 3 | extended RX FIFO: WriteRegMem32 0xF30028 = 0x804400, 0xF30030 = 0x3E8 | DS 5.3.3 |
| 4 | read both back (ReadRegMem32): base 0x804400 or 0x004400, size 0x3E8 | SDR (ROM 1.24 drops the alias bit on read) |
| 5 | clear FIFO IRQ flags: 0x0114 `3F 3F` | DS |
| 6 | SetRx 0x020C, timeout 0xFFFFFF (continuous) | DS |
| 7 | read the FIFO registers back again (the route or RX start mustn't have changed them) | SDR |
| 8 | ClearRxFifo 0x011E, then clear the flags again (drops what arrived during the start) | SDR |

- **R2.4** The route payload's byte 5 selects the destination: 0x0A is the RX FIFO; 0x92 is an on-chip SRAM window
  (not used here). The other ten bytes are given as-is; their meaning isn't known.
- **R2.5** CalibFE overwrites the extended FIFO's memory (DS 5.3.3): calibrate before step 3, never during a
  session. A retune is therefore a new session (2.5).
- **R2.6** The 1 KB FIFO is optional to the chip but needed in practice: with the default 256-byte FIFO the host
  has 512 us at 125 kS/s between reads, and SDR's tests overflowed within 150 ms; with 1 KB (2 ms) they ran 391 s
  without loss.

### 2.3 Samples

- **R2.7** Each sample is 4 bytes: I then Q, each a signed 16-bit little-endian integer. I + jQ has positive
  frequency for a signal above the tuned frequency (SDR, measured with tones at +25 and -15 kHz).
- **R2.8** The rate is 4 times the LoRa bandwidth: 125 000 complex samples a second at 31.25 kHz, 250 000 at 62.5
  kHz (SDR, measured with known tones to about 0.5%: a measured rate, not a crystal-exact one).
- **R2.9** 125 kS/s ran continuously for 391 s on SDR's board. 250 kS/s ran clean in 40 ms captures only;
  continuous 250 kS/s is unproven. 500 kS/s and faster overflow the FIFO: 16 MHz SPI (DS 3.7.2) can't carry them.
- **R2.10** The chip's filter ahead of the source passes about the LoRa bandwidth, not the rate. Tones at +25 kHz
  and -15 kHz came through at 62.5 kHz bandwidth (250 kS/s). At 31.25 kHz (125 kS/s) the W12's noise floor showed a
  hump about +-20 kHz wide, falling off outside it, and DMR channels 25 kHz from the center weren't there; one 5 kHz
  off decoded (2026-10-23). The firmware lets channels go within +-(rate/8 - 7.6 kHz) of the center: +-8 kHz at
  125 kS/s.
- **R2.11** Gain: fixed steps 12 and 13 (SetAgcGainManual, DS 7.3.9) did as well as the AGC on weak signals; the
  AGC was about 20 dB worse on strong ones (SDR). Image rejection was about 41 dB at 433.9 MHz (SDR).

### 2.4 Reading

- **R2.12** Read the level with GetRxFifoLevel (0x011C, 2 bytes, big-endian), then read whole samples (a multiple
  of 4 bytes, at most 256 bytes a frame) with the direct FIFO read (0x0001: the data follows the two status bytes
  in the same frame, DS 5.4.1.3).
- **R2.13** A level of 1024 or more means the FIFO filled and samples were lost.
- **R2.14** Check GetFifoIrqFlags (0x011B: RX flags then TX flags) at least every 1 KB. RX overflow (0x10) or
  underflow (0x20) means lost samples, and the samples since the last good check can't be trusted. Don't clear the
  flags during a session: a loss must stay visible until it's handled.
- **R2.15** On a loss, end the session (2.5) and start a new one: the stream has a gap of unknown length.
- **R2.17** The samples are small: about +-5 counts on noise at gain step 13 (W12, 2026-10-23), so the noise floor
  is near the quantization. Gain 13 didn't change that. Whether the route can scale them isn't known.
- **R2.18** On an ESP32-S3, 1 KB is 2 ms at 125 kS/s. A reader under Wi-Fi's task priority lost samples about every
  5 s idle and several times a second during a call; above it (24), none in minutes, through calls. Waiting a tick
  only when less than one 256-byte read is ready keeps it from starving its core.

### 2.6 Rates, sources and the rate converter (W12, 2026-10-23/24)

Measured on our W12 with ROM 1.24, and read from the ROM's code (facts only; nothing of it is copied here).

- **R2.19** Under the FSK modem (packet type 2), SetFskModulationParams' rx_bw byte sets the route's rate when route
  byte 0 is 0xFF: bits 2:0 are log2(decimation / 4), bits 5:3 the mode − 1, bits 7:6 the channel filter. The rate
  is 32 MHz / (mode × decimation), crystal-exact. Measured: 0x1C 125.4 k, 0x1B 250.4 k, 0x13 333.2 k, 0x12 664.8 k
  (666.7 nominal). Only the codes in the datasheet's table 11-4 are accepted (0x30, mode 7, was refused by both
  SetFskModulationParams and the route). The channel filter's 3 dB width is 0.37–0.38 of the rate with bits 7:6 = 0,
  then 0.34, 0.30, 0.27. Route byte 0 can carry the code itself under FSK; under LoRa an explicit code gave no
  samples.
- **R2.20** Route sources (byte 5 bits 2:0), bytes a sample on the FIFO: 0: 2, 1: 2, 2: 4, 3: 4, 4: 4, 5: 4, 6: 2.
  Source 1 is int8 I then Q after the channel filter; source 2 int16 I then Q after it; source 3 behaves as 2;
  sources 0 and 6 come through the rate converter (R2.21), 0 as int8 I then Q, 6 with an offset (rms about 11,
  probably frequency); source 4 carries 9-bit values in the top of 16 and comes faster than 16 MHz SPI can read.
  Source 1 streamed continuously at 664.8 kS/s (1.33 MB/s) at 16 MHz SPI with no loss.
- **R2.21** Sources 0 and 6 pass through a rate converter whose output rate is route bytes 1–4 (big-endian, in Hz;
  with bit 31 set, in 1/256 Hz), from the rate code's rate (byte 0). Its ratio, code rate / output rate, must stay
  under 4. The output is exact to the 32 MHz crystal. Measured: 576000 from 800 k (code 0x21) and from 1 M (0x19),
  384000 from 500 k (0x1A) and 800 k (0x21), 288000 from 333.3 k (0x13), all continuous at 16 MHz SPI with no
  loss. The passband is the code's channel filter (0.37 of the code's rate), so with 800 k into 576 k it was 289–294
  kHz wide. A rate of 0 makes the route answer an error but still sets the source.
- **R2.22** The FIFO's size field (0xF30030) holds at most 0x3FC: about 1 KB is the limit. Writes of 2, 3 and 4 KB
  read back 0x3FC.
- **R2.23** SPI above 16 MHz (the W12's pins go through the S3's GPIO matrix): 20 and 26.67 MHz read 10 240 words
  of ROM with no error at input delays of 0, 10 and 20 ns. At 40 MHz the data read back right only with 30 ns or
  more of input delay, and then every command left BUSY high: the chip misreads what it's sent.
- **R2.24** The ROM programs no digital gain or shift on the receive path. (Measurements of the level against the
  gain step before R2.25 was known all ran at step 13.)
- **R2.25** SetAgcGainManual (0x021A, one byte: 1 to 13, 0 the AGC) takes effect only in RX: SetRx sets
  0xF30154[23:16] to 0xDD (step 13) whatever was sent before it. Sent in RX, the step lands in both nibbles (step 1:
  0x11, 0 for the AGC: 0xD0). Send it after SetRx, and again after any SetRx. The steps' gains, from the table at
  0xF30174 (bits 9:0, signed, 0.25 dB): −8, −2, 4, 9, 14, 18.25, 22.5, 28, 32.5, 38, 43.25, 47.5, 53.5 dB.
- **R2.26** The 2-byte sources (0, 1; 6 untested) clip at −32 and +31: 6 bits of range in int8. Source 1 is about
  half of source 2's value (rms 3.4 against 7.0 at step 7, 915 MHz). Source 2 (int16) passes at least ±4 500 without
  clipping (bursts in the 915 MHz band at step 13). So from the noise to clipping, int8 gives about 20 dB and int16
  at least 50 dB more. A strong signal anywhere in the band clips the whole int8 stream.
- **R2.33** (W12, 915 MHz, 2026-10-26) The int8 clip is a hard one, not unused range: at step 13 (source 0, 400 k),
  1.6 M values all lay in −32..+31, with 1.08 % at −32 and 1.25 % at +31 against 0.16–0.18 % one step in. With
  the noise alone, int8's rms against the step: −8 dB 3.1, 9 dB 4.8, then 13 from 28 dB up (clipped). Int16's (source
  2, 250 k): 1.5, 4.3, 30, 160, 544 at −8, 9, 28, 43.25, 53.5 dB, with no pile-up; at 53.5 dB it spanned −5 114 to
  +4 364. The AGC (step 0) doesn't allow for int8's range: under it, int8 at 400 and 576 k had rms 18–20, mostly at
  the rails. For int8, a fixed step near 9 dB leaves the noise at rms ~5 and about 16 dB above it.
- **R2.28** In the wide mode a loss needn't end the session: ClearRxFifo and ClearFifoIrqFlags, and the next bytes
  are whole samples again (int8 at 576 k and int16 at 240 k decoded after it). A new session takes about 30 ms; at
  int16 288 k each one was followed by another loss, 25 a second, the stream down most of the time.
- **R2.29** Throughput over the W12's SPI with the firmware's reader (a level query, then a DMA read, by the level):
  at 16 MHz about 1.6 MB/s while reading. int8 576 k (1.15 MB/s) keeps the SPI busy about 93% of the time; int16
  333.3 k (1.33 MB/s) lost about 70 times a second at 16 MHz and 0.4 at 20 MHz; int16 250 k (1 MB/s) lost none.
- **R2.30** A direct FIFO read may end mid-sample: the next read continues from the byte after it, with no loss
  (W12, 2026-10-24: reads of n - 2 bytes, n a multiple of 4, so the whole frame is a multiple of 4; int8 384 k
  129 of 131 bench bursts, int16 240 k 130 of 131). So R2.12's "whole samples" is the reader's job, not the
  chip's: the reader keeps the part sample for the next read, and drops it whenever the FIFO is cleared.
- **R2.31** Sending the FIFO read's opcode as an SPI command phase (ESP-IDF `SPI_TRANS_VARIABLE_CMD`, the 2 opcode
  bytes outside the data) instead of in the frame lost samples continuously (W12, 2026-10-24). Why isn't known;
  the opcode goes in the frame's first two bytes.
- **R2.32** ESP32-S3, ESP-IDF 5.5: with the SPI bus on DMA, a transfer whose receive buffer isn't 4-byte aligned
  or whose receive length isn't a multiple of 4 gets an internal bounce buffer allocated for it, every time. When
  that allocation fails, the driver's clean-up copies from NULL (LoadProhibited in the reader task; the W12 has
  about 10 KB of internal RAM free while streaming). Keep FIFO frames (2 status bytes + data) a multiple of 4 and
  the buffers aligned; checking the free size (a 2 KB margin) refused every read, and checking the largest free
  block on every transfer was too slow for the stream.
- **R2.34** (W12, ESP32-S3 at 240 MHz, 16 MHz SPI, 2026-10-26) The reader's cost is per read, not per byte. Reading
  by the level whatever had come in (300–400 bytes at a time) cost about 90 us a read besides the bytes: a level
  query (two frames, 17.6 us each through ESP-IDF's polled transfer, about 3 us of it on the wire), BUSY (7–10 us
  a frame) and the DMA read's set-up (about 40 us). At 576 k int8 that kept the SPI busy about 90% of the time and
  the reader on core 0 42% of it (int16 250 k: 49%), and it never slept: the FIFO was always past the IRQ level.
  Moving the reader's code into IRAM, and holding the SPI bus between transfers, changed neither. Waiting for about
  640 bytes and querying the level only every fourth read, the level in between reckoned from the rate less a
  64-byte margin, took it to 21% (576 k), 19% (250 k int16), 11% (125 k int16) and 6% (48 k), the SPI busy about
  64% at 576 k. Over USB, 576 k and 250 k int16 delivered 100% for 60 s each with no loss. The wait between reads
  needs a sleep under a tick: an esp_timer one-shot (ISR dispatch) waking the task.
- **R2.35** (W12, 384 k int8, five channels, 2026-10-27) The front end's `read` hands the DSP whole chunks. It used
  to return what the ring held once the first block (1 ms) came, so a DSP with time to spare took chunks of a
  millisecond or two, and the per-chunk costs grew into the time: the DSP load read 0.94 with five channels and
  with six, core 1 99%. Waiting up to the timeout for the 4096 samples asked for, six channels went to 0.90, core 1
  94.5%. A chunk is 10.7 ms at 384 k, the size the RTL-SDR's USB transfers already gave.
- **R2.27** The noise floor is set after the gain. On the W12 at 461 MHz (through the 902–928 MHz SAW), the noise
  doesn't move from step 1 to 13 (source 1, about 2 counts rms) while a bench carrier rises with the step: the
  floor there is the chip's own, after the gain. At 905, 915 and 925 MHz with the GC1109's LNA on, the noise rises
  above it from step 10 (robust σ about 9 at step 10, 12 at 13, against 1.5–3 with the LNA shut down). RX boost
  (SetRxPath byte 3, 0 to 7) changed a 461 MHz carrier's SNR by under the measurement's spread (±1.5 dB).

### 2.5 Ending a session

- **R2.16** SetStandby, then a reset (NRESET), then set the chip up again from scratch (calibration, 2.1). SDR
  always resets after a raw session; whether the route can be undone without a reset isn't known.

## 3. Transmit

R3.1–R3.8 are SDR's facts as first recorded. R3.9 on are measured on our W12 (ROM 1.24) on 2026-10-24, received
on the SDR bench: at 461.3375 MHz with the GC1109 in TX bypass (through the board's 17.8 dB pad, PA mode never
used there), and at 920.0 MHz with the GC1109 in TX bypass (much stronger at the receiver: the part is matched for
the 900 MHz band). Where a fact below corrects R3.1–R3.8 it says so.

### 3.1 SDR's facts

- **R3.1** Opcode 0x0293, 7 bytes: sample count N (16 bits, big-endian), sample rate in samples a second (32 bits,
  big-endian), selector (1 byte) (SDR). Then samples go into the TX FIFO and SetTx (0x020D, a 24-bit timeout in
  1/32 ms, DS 6.3) sends them. TX_DONE (IRQ bit 19, DS table 5-20) marks the end.
- **R3.2** Selector 0: interleaved signed 8-bit I, Q (2N bytes). Selector 1: signed 8-bit frequency samples, N
  bytes, at `sample × fdev / 64` Hz, where fdev is SetFskModulationParams' deviation (measured at fdev 10 kHz:
  156.28 Hz a count). Selector 2: signed 8-bit phase steps of `sample × 2π / 128` radians a sample (SDR).
- **R3.3** Set up first, in standby: SetPacketType FSK (0x0207, 0x02), SetFskModulationParams (0x0240: bit rate =
  the sample rate, pulse shape 0 (none), an RX bandwidth, fdev), SetFskPacketParams (0x0241: fixed length, payload
  N bytes), the PA (SetPaConfig 0x0202, SetTxParams 0x0203), SetRxTxFallbackMode (0x0206) to standby, then 0x0293
  (SDR's order). For selector 0 with amplitude, OOK (packet type 0x0A) setup is needed instead; with FSK setup the
  envelope stays constant.
- **R3.4** Rates: with selector 1, 125 000 S/s gave the full deviation; 76 800 gave half, and 38 400 inverted it
  (SDR). **Not so on our board: R3.10.**
- **R3.5** Length of a run: SDR capped selector 0 at 32 767 complex samples, for a 16-bit byte count; R3.12 has what
  we measured. The TX FIFO must be refilled during a run (1 KB TX FIFO: 0xF3002C = 0x804000, 0xF30034 = 0x3FC, DS
  5.3.3), polling GetTxFifoLevel (0x011D).
- **R3.6** After a run: standby, reset, set up again (SDR). **Not needed: R3.16.**
- **R3.7** Selector 0 saturates near magnitude 64 and abrupt phase reversals come out wrong (SDR). What's behind
  both: R3.22–R3.26.
- **R3.8** SDR's FSK setup also sent a preamble length and a sync word **(choice)**. **Nothing of them goes on air:
  R3.11.**

### 3.2 Frequency samples (selector 1)

- **R3.9** The setup (in standby): SetPacketType FSK, CalibFE at the frequency, SetRfFrequency, SetPaConfig,
  SetTxParams, SetRxTxFallbackMode, SetFskModulationParams (bit rate = the sample rate, shape 0, rx_bw any valid
  code, fdev), SetFskPacketParams, the 1 KB TX FIFO (after CalibFE: CalibFE overwrites that memory, R2.5),
  ClearTxFifo, 0x0293, then the FIFO prefill and SetTx. With the default 256-byte FIFO the samples came out garbled.
- **R3.10** The scale is `sample × fdev / 64` Hz exactly, the same at 31 250, 38 400, 48 000, 62 500, 76 800,
  96 000, 125 000 and 250 000 S/s (fdev 2048: 32 Hz a count). Any of those rates works. (Corrects R3.4.)
- **R3.11** A run lasts N / rate exactly, and the FIFO drains at the sample rate. Nothing goes on air ahead of the
  samples, even with a 256-bit preamble and a 32-bit sync word configured. Key-up has a settling transient of about
  1 ms.
- **R3.12** N = 65 535 works (0.52 s at 125 kS/s). N = 0 sends nothing, doesn't consume the FIFO, and stays in TX
  until SetTx's timeout (IRQ bit 21). Selector 0 ran 31 250 complex samples (62 500 bytes) with no wrap; past 64 KB
  it does wrap, as R3.5 had it (R3.43).
- **R3.13** Underflow: the chip holds the last sample's frequency until N samples have passed, and sets TX FIFO flag
  0x20. Samples written to the FIFO after the underflow are never sent. The FIFO must not run dry.
- **R3.14** Commands during a run: SetFskModulationParams answers OK and changes the deviation live; WriteRegMem32
  answers OK; 0x0293 again answers OK but doesn't extend the run; SetRfFrequency answers CMD_FAIL and SetTxParams
  CMD_PERR.
- **R3.15** Back-to-back runs: on TX_DONE, clear the IRQ and send SetTx again (the 0x0293 setup persists), with
  fallback FS or standby RC. The host takes 0.31–0.34 ms to restart; on air each seam is a dip of −21 to −25 dB
  for 180–500 µs. That's the only way past 65 535 samples.
- **R3.16** No reset is needed between runs, or between RX and TX. From a running raw RX session (R2.19), TX setup
  without reset or CalibFE took 10 frames and 1.49 ms, and the burst was right on air; back to RX took 12 frames
  and 1.15 ms, and samples flowed with no overflow. CalibFE alone takes about 10.6 ms and isn't needed for TX at a
  frequency already calibrated for RX. (Corrects R3.6.)
- **R3.17** A run sometimes ends after about 0.9 ms with TX_DONE, TX FIFO flags 0x18 (full and overflow) and nothing
  on air. It happened on a run's first try, several times in a day, and never twice in a row: send it again. At
  feed rates near the host's limit a run also ended early with flags 0 (R3.28). Cause not known.
- **R3.18** Selector 2 is a phase step a sample: `sample × rate / 128` Hz (375 Hz a count at 48 kS/s), whatever the
  fdev. (Confirms R3.2.)
- **R3.19** DMR by frequency samples: 4-FSK at 4800 symbols/s, ±648 / ±1944 Hz, shaped with a root-raised-cosine
  (α 0.2) in the host, at 48 kS/s, fdev 2048. 32 of 32 bursts decoded (bench decoder) with 0 FEC errors, mean
  symbol error 0.10, 99% bandwidth 7.7 kHz.

### 3.3 The chip's 4-FSK modem

- **R3.20** Opcode 0x023B with argument 0x01, sent after SetPacketType FSK and before SetFskModulationParams,
  turns the FSK modem into a 4-FSK modem (found in the ROM; 0x023B 0x00 is plain 2-FSK). Bit rate is twice the
  symbol rate (9600 for 4800 symbols/s). The levels are ±20 and ±60 in fdev / 64 units, so fdev 2073.6 Hz gives
  DMR's ±648 / ±1944 Hz. Dibits go MSB first; chip dibit 00 → −1, 01 → −3, 10 → +1, 11 → +3. DMR's (00 → +1,
  01 → +3, 10 → −1, 11 → −3) is the chip's with bit 1 flipped: XOR each byte with 0xAA. Set the payload length
  in SetFskPacketParams and send the burst as an ordinary packet (no preamble, no sync word, SetTx).
- **R3.21** 32 of 32 DMR bursts decoded with fdev 1944 (outer levels 1822 Hz): with shape 0 (none), 0 FEC errors,
  symbol error 0.18, 99% bandwidth 7.1 kHz; with shape 0x05 (Gaussian), 1 corrected bit, symbol error 0.34, 5.6
  kHz. With shape 0x0C (RRC) 27 of 32 decoded, symbol error 0.49, 5.1 kHz. The longest burst tried was 1152 bytes
  (0.96 s). The documented 2-FSK packet (no 0x023B, 4800 b/s) ended at 6.5 ms with nothing on air in our setup:
  not understood.

### 3.4 I/Q samples (selector 0)

- **R3.22** Under FSK (and packet type 0x0B, which the ROM treats as raw I/Q) only the phase reaches the air: the
  carrier follows I/Q's angle at constant power, zeros included. Under OOK (packet type 0x0A, SetOokModulationParams
  0x0281: bit rate = the sample rate, shape 0, rx_bw, depth) the magnitude drives the PA too: a polar transmitter.
  All-zero samples turn the PA off (the noise floor).
- **R3.23** Amplitude is the PA's output power, between its floor and the power SetTxParams set. The floor is the
  same absolute level whatever the setting: −30.6 dB below +22 dBm, −19 dB below +10, −11 dB below −2 (920 MHz).
  So the range is widest at +22. (All TX tests here used SetPaConfig LF duty 4, slices 2: DS table 7-19's setting
  for about +14 dBm; its +22 dBm setting is 7 and 7. The levels below are for that PA setting.) At +22 dBm, 920 MHz,
  slow steps: magnitudes under about 40 all give the floor;
  48 −23.6 dB, 56 −17.2, 64 −13.2, 72 −10.0, 80 −7.2, 96 −4.1, 112 −1.8, 127 0. At 461 MHz the curve differs
  (+22: flat from 64 up). The curve a waveform at 48 kS/s sees differs again (fitted from a two-tone: 14 −12.9 dB,
  26 −6.6, 38 −3.1, 50 −0.8, flat from about 60), so fit the curve with a waveform at the rate to be used. AM-PM is
  about −40° at the bottom, under 10° from half scale up. Magnitudes past 127 (I and Q both large) add nothing.
- **R3.24** Phase is reproduced from step to step: where the magnitude is high, each sample's phase step comes out
  within 1–2°. The chip accumulates the steps, so a step it gets wrong leaves a lasting phase offset.
- **R3.25** The instantaneous frequency the phase path follows is limited. A tone comes out right up to the limit,
  and as some other frequency past it (not a clean wrap). The same under OOK and under FSK at any fdev:

  | Rate (S/s) | Right up to | Wrong from |
  |---|---|---|
  | 24 000 | 9 kHz | 10 kHz |
  | 48 000 | 15 kHz | 18 kHz |
  | 96 000 | 20 kHz | 25 kHz |
  | 125 000 | 20 kHz | 30 kHz |

  A chirp from −10 to +10 kHz at 125 kS/s tracked throughout. Near the origin of the I/Q plane a waveform's phase
  steps grow past the limit, and the phase is lost there (R3.24): QPSK and OFDM lost tens to hundreds of degrees
  over 40 ms while their step-to-step phase was right.
- **R3.26** Hold, not interpolation: each sample's value is held, with some smoothing. A tone at f has images at
  f ± k × rate: at 48 kS/s a 3 kHz tone's first image was −23 dBc (a pure hold gives −24); a 5 kHz tone's was −33
  dBc at 166.7 kS/s, −36 at 200 k, −41 at 250 k, −44 at 312.5 k.
- **R3.27** What a polar transmitter gets from it (920 MHz, +22 dBm, a 40 ms block sent 10 times, the received
  copies averaged; NMSE against the ideal waveform after removing gain, delay and frequency offset):

  | Waveform (48 kS/s) | As sent | Fitted AM / AM-PM table | Table + minimum magnitude 0.1 | Table + minimum 0.2 |
  |---|---|---|---|---|
  | QPSK, RRC α 0.35, 4800 symbols/s | −6.2 dB | −6.6 dB | −20.3 dB | **−29.5 dB** (−24.3 single pass) |
  | OFDM, 16 QPSK carriers 500 Hz apart | +2.4 dB | | | −7.8 dB |
  | Two-tone ±500 Hz | −12.2 dB | | | |

  The minimum magnitude ("hole punching"): samples under r_min of the peak are pushed out to r_min, their phase
  interpolated across the dip, which keeps the phase steps under the limit (R3.25). The table alone fixed the
  amplitude (−35 dB AM error) but not the phase. OFDM is still phase-limited at 48 kS/s; at 96 kS/s it's untested
  (those runs didn't complete).
- **R3.28** Feed rate: I/Q runs completed at 166.7, 200, 250 and 312.5 kS/s (625 kB/s through the FIFO). At 500 kS/s
  (1 MB/s) the host's fill loop (level query, write, by the level) didn't keep up and the run ended at 35 ms.

### 3.5 Carrier, retune

- **R3.29** SetTxTestMode (0x020E) 2 is a plain carrier with no timeout; 1 is a carrier too here (the FIFO isn't
  used). Our W12's carrier sat +188 Hz from the channel after the −28 ppm crystal correction, cold, and drifted up
  with heat to +400 Hz at 461 MHz and +950 Hz at 920 MHz over a session (no TCXO).
- **R3.30** 0xF40144 holds the PLL's frequency word: `round(hz × 2^20 / 10^6)` (0.954 Hz steps), hz being the
  corrected frequency. Writing it with WriteRegMem32 during TX retunes the carrier live with no dip in power: 5 kHz
  settled in 0.1–0.3 ms, 100 kHz in 2–3 ms (CW, 920 MHz). 0xF40140 reads 0x1041 in FS and 0x840 in TX; pulsing its
  bit 31 with the FS value during TX broke the carrier (the ROM's own retune pulses it, with recalibration around
  it). Whether a write of 0xF40144 retunes a selector 0/1 run as well isn't tested.
- **R3.31** The documented way: SetFs, SetRfFrequency, SetTxTestMode 2 again. The frequency changed in 50–250 µs
  but the PA was off in FS: a −17 to −20 dB dip of about 270 µs.

### 3.6 What the gateway does with it

DMR is 4FSK, constant envelope: selector 1, with the frequency from the modulator (`rdof_mod_freq`), fdev 2048 Hz
**(choice: 32 Hz a count, ±1944 Hz is ±61 counts)**, at 48 000 or 125 000 S/s (R3.10). One run per TDMA burst
(`lr2021_iq_transmit`, keyed up at the burst's time, R3.48); switching between RX and TX takes 1.2–1.5 ms with no
reset (R3.16). The driver's TX API (`components/lr2021`, `lr2021_tx.h`, `lr2021_iq.h`) covers every path above.

### 3.7 The documented modems

Measured on a W12 (ROM 1.24) on 2026-10-24 with the driver's packet API (`lr2021_packet_send` / `_receive`).

- **R3.32** Packet TX works without the patch at 920 MHz. Time on air, from the chip's TX_DONE against the
  datasheet formula: LoRa SF7/125 kHz 51.9 ms (51.5 predicted), SF9 165.4 ms (164.9), SF7/500 kHz 13.8 ms (12.9),
  FSK 5.4 ms (4.2), OOK 72 ms (73.3), FLRC 1.9 ms (1.28); the extra is the ramp and the PLL. An FSK packet decoded
  from the SDR byte for byte with its CRC, and LoRa's preamble, sync word 0x12 and downchirps were there. The same
  setups give the same results with the patch running.
- **R3.33** FSK whitening on air is PN9 (seed 0x1FF) with each byte's bits reversed; the IBM CRC covers the length
  byte and the payload.
- **R3.34** The packet API has to start from standby: ClearRxFifo / ClearTxFifo are refused while the chip is in RX
  or TX, so a call that finds it receiving fails unless it sends SetStandby first.
- **R3.35** **FSK packet RX needs a patch running.** Without one, FSK RX (4800 b/s, fdev 1300, rx_bw 0x1E, 24-bit
  sync, the bench's DMR signal at 461.3375 MHz) never finds a preamble or a sync (GetFskRxStats all 0) and the RX
  FIFO fills with small int8 values, I/Q-like, only while a signal is present. With Semtech's patch, or with a
  31-word patch of our own that only writes the marker and returns, the same setup counts every burst (pkt_rx =
  pbl_det = sync_ok, RX_DONE, PreambleDetected, HeaderValid IRQs) and the FIFO holds the packets. EnablePram without
  a valid image doesn't help, nor do the patch's DCDC values (0xF20024 [23:20] = 8 and bit 13 clear, 0x80004C =
  0x2CCCCC) set by hand, nor the route command with destination 0, nor the SRAM bank 1 owner field (aux
  0x80000008 [5:3], which a successful enable sets to 001; it reads 0 after a reset, and 001 or 000 written by hand
  changes nothing). What in the ROM depends on an active patch isn't known yet; any running patch is the fix.
- **R3.36** 4-FSK RX (variant 0x023B 1, 9600 b/s, fdev 2073, the DMR sync in chip dibits) with the patch: a 48-bit
  sync never matches (preambles found, every sync failed); a 24-bit one (the sync's last 12 symbols, length byte
  0x98) matches each burst, but the payload symbols agree with the SDR's no better than chance (54 % wrong at the
  best mapping and offset). The variant changes only the transmitter: the demodulator registers (0xF30C00–0xF30C3C)
  read the same as for 2-FSK at the same bit rate, so the chip receives 2 levels. 4-FSK RX for DMR needs a
  demodulator setup of our own (Semtech's patch has one for WM-Bus N 19.2 kb/s 4GFSK). Without a patch it behaves
  as in R3.35.
- **R3.39** WM-Bus N 19.2 (4GFSK) sets 0xF30C00 bit 16 and 0xF30904 bits 0, 2 and 14 (bit 13 clear), which plain FSK
  with the 4-FSK variant doesn't. Set by the host after SetRx (Semtech's patch running, 9600 b/s, fdev 2073): the
  48-bit DMR sync still never matches; a 40-bit one matches a few bursts only with the polarity inverted (the sync
  register holding DMR's own dibit values); the payload symbols still disagree with the SDR's (about 55 %), and one
  of each symbol's two bits is almost always 0. A ±1 kHz retune changes nothing. With these settings, a packet RX that
  ends in its timeout sometimes leaves BUSY high (the chip needs a reset); without them it doesn't (W12,
  2026-10-24).
- **R3.37** SetRssiCalibration with the datasheet's 868–915 MHz LF table (as `lr2021_radio_set_rssi_cal` encodes
  it) leaves the boot values at 0xF30174–0xF301A4 unchanged: the encoding and the gain signs match the ROM's own
  (gain in bits [9:0] as a signed 10-bit count, noise figure in bits [23:16], one entry a word). The 490 MHz table
  writes its own values the same way.
- **R3.38** GetTemp (VBE source, 13 bits) gave 42.97 °C in degrees format (0x2AF8: bits 15:3 a signed count of 1/32
  degree) and 44.5 °C from the raw format's formula (0x1082); GetVbat gave 2448 mV in mV format (0x0990) and 2.448 V
  from the raw formula (0x1202). The two formats agree, so the driver's parsers do. Whether 2.45 V is the W12's real
  supply to the chip wasn't checked.

- **R3.40** **4-FSK RX of DMR works** with a patch running (Semtech's, or ours alone: `components/lr2021/pram`). The
  order matters: SetPacketType FSK, then 0x023B 0x01, then SetFskModulationParams (the setter reads the variant;
  R3.36 and R3.39 had it after, so the chip set itself up for 2 levels). Then 9600 b/s, shape 0x05 (or 0), rx_bw
  0x1E, fdev 1944; SetFskPacketParams with no preamble detector, fixed length, no CRC, no whitening; the 48-bit sync.
  The ROM's correlator doesn't suit DMR's sync, so these are written after setup (our patch's 0x02F0 table): 0xF30C18
  = 0x004D263D and 0xF30C1C = 0x00B2D9C2 (the 24 symbol signs of BS data and of BS voice, LSB first), 0xF30C20
  [21:16, 6:0] = 3, 0x57, 0xF30C24 = 0xF8FF4001 (mask 0xF8FFC003), 0xF30C14 [6:0] = 0x0C, 0xF30824 = 0x7D75DF5D,
  0xF30820 = 0xD7DF75F7, 0xF30828 [6:0] = 32. Each bench BS burst then gives PreambleDetected, sync and RX_DONE, and
  the payload's symbols come out in the TX coding (00 −1, 01 −3, 10 +1, 11 +3; DMR's dibit is the chip's XOR 2),
  starting right after the sync. Against the SDR's decode of the same bursts (52 symbols each): some bursts are
  exact, the median is 5–15 wrong symbols a burst, varying more from run to run than between settings. Most errors
  are an inner symbol read as the outer one on its side, and they peak mid-burst. Shape 0x0D and fdev 2400 are worse.
  With Semtech's patch a packet RX that ends in its timeout sometimes leaves BUSY high; with ours it hasn't (W12,
  461.3375 MHz, 2026-10-24). The driver's `lr2021_fsk4_dmr_rx` makes this setup.
- **R3.41** The chip's 4-FSK errors are its demodulator's, not the signal's. The bench bursts arrive at about
  −122 dBm (rssi_sync), LQI about 8 dB. The same call through the raw I/Q route (384 kS/s int8), demodulated offline
  (FM discriminator, RRC 0.2 matched filter, timing and levels from the sync), gives 0–3 wrong symbols in 52, about
  1%; the chip gives a median of 6–14, about 15%. The chip's errors come in runs, at the same places in repeated
  payloads: runs of one inner symbol come out alternating (−1 −1 −1 as −3 +1 −3), which looks like a tracking loop
  ringing. They aren't symbol slips. The median moves 2× between runs of the same setup (each from a reset), more
  than any change tried: rx_bw 9.6–14.9 kHz, a −115 Hz retune (the offset the I/Q shows), 0xF30C28's other fields
  and 0xF30C3C as WM-Bus N has them (W12, 2026-10-24).
- **R3.42** Command 0x022F (one byte into 0xF30C28 bits 28:24, 22:21 and 20; the ROM leaves it 0 for FSK, WM-Bus
  sends 0xFD) sets the 4-level demodulator up much better for DMR with bit 0 set (0xF30C28 bit 20). With the R3.40
  setup, sent after the sync word: 0x00, 0x04, 0x08, 0x10, 0x20, 0x40, 0x80, 0xF8 and 0xFC give a median of 7–15.5
  wrong symbols in 52; 0x01, 0x03, 0x05, 0xFD and 0xFF give 3–5 (0x05: 3, mean 3.1–5.2). So about 6% of symbols
  wrong instead of about 25%, still above the 1% of R3.41. The driver sends 0x05 (W12, 461.3375 MHz, 2026-10-24).

- **R3.43** An I/Q run's bytes are a 16-bit count: a run of N samples ends after (2N mod 65 536) bytes, TX_DONE with
  the FIFO still holding the rest (flags 0x04). 32 750 samples went out whole at 125 kS/s, 32 812 ended after
  88 bytes; runs of 38 400, 48 000 and 64 000 samples ended at their byte counts mod 65 536. So I/Q runs are at most
  32 767 samples, as R3.5 had it (W12, ROM 1.24, iq_polar and iq_phase, 2026-10-26).
- **R3.44** Seams on the W12: with the board's RF switch table, all three DIOs go low between runs (the GC1109 in
  shutdown), and each run after the first came back 22–28 dB low for 5–13 ms before full power, whatever the
  fallback (FS or standby RC) and with SetPaConfig and SetTxParams sent again. The tone stayed on its frequency
  through it. With the TX pattern also set for standby (mask bit 0) during the transmission, the seams are 0.2–0.5
  ms, as R3.15 had them, at 48, 96 and 125 kS/s. The host's part of a restart is about 260 µs. The GC1109's bypass
  passes the chip's output about 34 dB below its PA path (a 17.8 dB pad, then the PA's 30 dB), so the W12's antenna
  gets about the chip's power + 12 dB, up to about +27 dBm. Setting 0xF30800 bit 14 before SetTx didn't make a run
  continuous: TX_DONE still came at the run's length (W12, ROM 1.24, 2026-10-26).
- **R3.45** Shorter seams (W12, ROM 1.24, 2026-10-26): most of R3.44's seam was the host. Its loop read the IRQs
  and the FIFO level over SPI each time round (four frames, about 100 µs) and waited 100 µs between looks, and a
  1 KB FIFO write (about 0.5 ms at 16 MHz) could hold up a restart. With TX_DONE and TIMEOUT on the IRQ DIO, the
  pin watched from 150 µs before a run's reckoned end, SetTx sent on its edge before any status read, and no FIFO
  write allowed to run past a run's end, SetTx goes out 28–33 µs after TX_DONE (114 restarts at 125 kS/s). On air
  the seams are then 81–85 µs below −10 dB for iq_polar and 102–135 µs for iq_phase (was 290–424 µs), at 96 and
  125 kS/s. The rest is the chip: TX_DONE comes about 66 µs after the run's length counted from SetTx sent, and a
  PA ramp of 4 µs instead of 32 µs didn't shorten the seam. SetTx sent during a run answers CMD_FAIL and changes
  nothing: the run ends at its length.
- **R3.46** Streamed bursts (W12, ROM 1.24, 2026-10-26, with SoapyLR20xx's bridge: this component behind a USB or
  Wi-Fi link, github.com/RadioFoundry/SoapyLR20xx): the bridge keys up once it has 0.2 s of samples and takes the
  rest into a ring as the burst goes out. A run whose data ends partway is cut with SetStandby once the TX FIFO
  reads empty, in place of zeros to the run's end: a 2 s burst at 96 kS/s measured 2.001 s on air. A 20 s burst at
  125 kS/s (5 MB, over twice the 2 MB ring) went out over USB with the FIFO never empty; key-up came 71 ms after the
  first TX_DATA (whole-burst buffering: about 1.5 s for 5 s). Refills held back near a run's end (R3.45) only while
  the run's last byte is already in the FIFO: a run that still needs bytes can't end, and holding them stalls it.
- **R3.47** SetTx ahead of TX_DONE (W12, ROM 1.24, 2026-10-26): the chip takes the next run's SetTx in the last
  45–60 µs before a run's TX_DONE, and starts that run as soon as the one before ends, without the host's 25–30 µs
  from the pin's edge to SetTx. Sent earlier it answers CMD_FAIL, holds BUSY about 82 µs, and the next run starts
  50 µs or more later than it would have: worse than not trying. BUSY isn't high before TX_DONE, so it can't mark
  the moment. TX_DONE's delay past a run's length from its start (its SetTx, or the TX_DONE before for one queued
  this way) is steady for a setup, ±11 µs: about 78 µs for iq_polar, 139 µs for iq_phase, 145 µs for freq at
  125 kS/s; the first run's (from standby) is longer. So the stream learns the delay for each way a run starts,
  sends SetTx 35–45 µs ahead of the predicted TX_DONE (10 µs later after a refusal), checks the chip is in TX at the
  edge, and sends SetTx then if not; lr2021_iq keeps what it learned for the next burst with the same mode and rate.
  Seams on air, 96 kS/s: 59–65 µs below −10 dB for iq_polar (was 81–92), 80–82 µs for iq_phase (was 102–135),
  81 µs for freq and phase_step (was 102–109). Over about 320 restarts at 125 and 250 kS/s: none refused, 70–100%
  of each burst's restarts queued (the rest on the pin).
- **R3.48** Timed key-up and turnaround (W12, ROM 1.24, 2026-10-26). A transmission's set-up to a filled FIFO takes
  2.8 ms from a receive session at the same cell and 12.6 ms with a CalibFE first (R3.16's 10.6 ms). A CalibFE
  holds through transmissions while nothing resets the chip, so a burst at the cell last calibrated, receiving or
  not, needs none: 2.7 ms. The SetTx frame takes 24–35 µs (BUSY, the SPI at 16 MHz): sent that much ahead, timed
  bursts key up within ±5 µs of the time asked, on the bridge's clock. Receiving at 125 kS/s, a 100 ms burst
  started 4.5 ms ahead left a 106–107 ms hole in the samples: about 2 ms to the first samples back.
## 4. Not known

- The exact passband at each bandwidth (R2.10), and whether the rate is exactly 4 × bandwidth.
- What scales the samples (R2.17).
- Whether a raw RX session can end without a reset (TX needs none: R3.16).
- Why a run sometimes ends at 0.9 ms (R3.17). (The documented 2-FSK packet of R3.21 does go out with a preamble
  and sync word: R3.32.)
- What in the ROM makes FSK RX depend on an active patch (R3.35); what 0xF30C28 bit 20 and the 4-level demodulator's other loop settings do (R3.41, R3.42).
- Polar I/Q at 96 kS/s and up with hole punching (R3.27); a retune by 0xF40144 during a sample run (R3.30).
